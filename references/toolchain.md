# Toolchain and compatibility

Editor evaluation target: **6000.7.0b3 arm64**. CLI versions in evaluation records describe tested commands, not a kit-wide required version; see the [beta.12 command check](../verification/cli-beta12.md). The [b3 upgrade record](upgrades/unity-6000.7.0b3.md) separates release-note changes, local installation checks and project-specific acceptance requirements. Earlier b1/b2 records retain their original version and do not qualify b3. Keep production, 6.7 UITK evaluation and future Unity 7 migration profiles separate. Native ProjectVersion.txt/packages-lock.json remain resolved-version authorities; this target is not an automatic choice for shipping games.

Record modules, CLI/checksum, Pipeline package, render pipeline, test/analyzer packages, .NET SDK, Blender/exporter, provider models, UI experimental flags, graphics APIs and validation date. Do not float latest/lts, Git main/current or CI installer channels in a template release.

Unity 6.7's documented language baseline is C# 9. A CoreCLR player or newer host SDK does not confer C# 14. C#9 is temporary; [language profiles](language-profiles.md) defines the intended C#14 transition and modern adoption gates. Adopt modern syntax incrementally; compiler, APIs, serialization, AOT and Burst compatibility are distinct checks. Candidate features: file-scoped namespaces/collection expressions; pure DTO records/init/required; small-service primary constructors; C# 14 extension members, field properties and span conversions; partial events/constructors only for justified generators. [Unity compiler](https://docs.unity3d.com/6000.7/Documentation/Manual/csharp-compiler.html), [Unity 7 announcement](https://unity.com/blog/unite-seoul-keynote-2026-recap), [C# 14](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-14).

## Lint enforcement

[Code quality](code-quality.md) owns nullable/compiler/analyzer/style enforcement; [developer tooling](developer-tooling.md) owns local setup and hooks.

Use the starter EditorConfig and a Roslyn-compatible Microsoft.Unity.Analyzers version. Install analyzers in the actual compiler hosts: Unity's documented analyzer import/scoping, and build-time style/analyzer settings in hand-maintained SDK projects. An IDE extension is insufficient. Keep generated/vendor code out of owned-code checks; prefer narrow suppressions and Unity-aware suppressors for serialized fields/messages. Prove a known diagnostic fails CI in a disposable change. Retain explicit `-analyzerconfig:.editorconfig` from the b1 finding until rejection probes on the selected Editor verify the actual compiler hosts; follow code-quality.md and inspect compiler arguments instead of assuming EditorConfig discovery. [Unity analyzers](https://github.com/microsoft/Microsoft.Unity.Analyzers), [diagnostics](https://github.com/microsoft/Microsoft.Unity.Analyzers/blob/main/doc/index.md), [Unity installation](https://docs.unity3d.com/6000.7/Documentation/Manual/roslyn-analyzers.html).

## CLI

Choose and record the CLI version per project; the kit does not impose one universal release. For a new project, evaluate a current compatible release. Existing projects retain their qualified pin until an intentional upgrade. CI installs/verifies that exact version and fails on mismatches; never self-update or use a floating installer channel during a build. A local self-update changes the shared executable, not project pins or compatibility evidence. Review affected commands and Pipeline compatibility before promoting a new pin. A CLI-only upgrade needs affected tooling checks, not an unrelated Editor migration or every player fixture.

Inspect the installed version's help/command manifest. Live Editor automation requires the matching Pipeline package. Create/modify serialized scenes/prefabs through Editor operations, preserve GUIDs, mark dirty/save, wait for imports/compilation; author C#/UXML/USS as text. Setup operations must be idempotent. Package installation can reload assemblies: persist/recover operation state or use an external coordinator; a static Editor polling callback cannot be assumed to survive. Judge completion by resolved native locks plus a successful import/compile, not by the polling helper alone. Pipeline connection failures require checking compilation/Safe Mode before retrying.

For beta.11-capable projects:

- **Fast compilation feedback:** after a coherent script edit, use `unity recompile --project-path /absolute/game --timeout 120 --format json` against the intended running Editor. Normal mode returns 0 for successful compilation, 6 for compile errors, and 7 if no Editor responds. Inspect diagnostics; connection failure is not a clean compile. Select `--strict` only when failing on all compilation warnings matches project policy. This does not replace semantic/style checks, tests or target builds. Older clients use their discovered Pipeline compile/status operations or the existing batch compile gate.
- **Version-aware API research:** from the game root, use `unity docs UIElements.VisualElement --url`; outside it, supply the project's actual `--editor-version`. Use `--manual`/`--search` where appropriate. Open and read the resulting page; URL generation alone proves neither page existence nor API support. Namespace-qualified documentation topics may be required. Older clients use the equivalent versioned official docs directly.
- **Detached work:** `unity job wait` may confirm dispatch and name a status command, not completion of the underlying operation. Discover the Editor's actual status operation and required arguments, retain its operation identity, and poll to a terminal result with a bounded timeout. Inspect errors and required current-run reports before declaring success. This completion contract applies on older clients too; beta.11 improves the message. Never invent a status command or repeatedly redispatch work to poll it.

### Beta.12-capable automation

Discover capabilities from the installed CLI and project Pipeline; do not infer them from the CLI version alone. [Migration/evidence](../verification/cli-beta12.md) records tested surfaces and remaining qualification.

- **Focused discovery:** prefer the tag index (`unity command --tags --project-path /absolute/game --format json`), then `--tag <tag>` for the relevant subtree. The index requires Pipeline 0.8.0-exp.1 or compatible later support. Older Pipeline versions fall back to the full catalog on bare `unity command`; explicit `--tags` fails instead. Consumers that need command rows must request `--detail compact` or `--detail full`, rather than assume a bare listing's shape. Reuse discovery within the session; refresh after relevant package/reload changes.
- **Readiness:** use `unity status --project-path /absolute/game --until-ready --timeout 120 --format json`, verify the returned project identity, and treat timeout/exit 6 as failure to become ready. `STATUS_PIPELINE_LOAD_PENDING` means the manifest contains Pipeline but the open Editor has not loaded it: wait for startup/import, focus the Editor if needed, and inspect Safe Mode/compile errors with `pipeline list`; do not repeatedly reinstall. Ready is not proof of gameplay progress; follow [scenario/capture readiness](test-scenarios.md).
- **Machine results:** prefer JSON for bounded responses. For NDJSON listings, separate rows from the terminal `type: result` envelope; require terminal success and reconcile `data.count` with rows when present. Empty results still have an envelope. Missing terminal output is incomplete evidence. An `open` success envelope proves launch dispatch, not import/readiness; never interpret empty stdout as success.
- **Failures/retries:** beta.12 waits within `command --timeout` for temporary unavailability and only resends work rejected before execution. Do not add blind retries of mutations with unknown outcomes. `recompile` exit 6 includes Editor-reported command failures; exit 7 includes dropped/timed-out transport requests. Inspect diagnostics and operation state before a bounded retry; neither is a passing compile. Interrupted run/test/import/player-launch commands can exit 130/143; retain incomplete status and diagnostics, never accept partial reports.
- **Exact inputs:** use full Editor versions; partial selectors now resolve an installed patch automatically. Review generated CI installers: beta.12's plain installer still floats unless replaced with the project's exact CLI acquisition/verification. Asset export on Unity 6.6+ signs by default and needs an authenticated organization; explicitly select signed distribution or `--no-sign` for intentionally unsigned output, never silently downgrade on failure.

Use `ci init` only when exposed by the installed CLI. Generator output needs review. [CI recipe](ci.md) owns build/test commands and runner setup. [CLI reference](https://docs.unity.com/en-us/unity-cli/unity-cli-reference), [release notes](https://docs.unity.com/en-us/unity-cli/release-notes).

## Upgrade acceptance

Review the candidate's incremental release notes and known issues, distinguishing them from cumulative stream features. Check content/archive backward compatibility; for the 6.7 archive transition, follow the [content rebuild and rollback guidance](upgrades/unity-6000.7.0b2.md#content-and-rollback). Pin a candidate on an isolated branch/copy; resolve modules/packages, compile pure and Unity code, exercise impacted fixtures, build/launch the target, inspect graphics/content and compare budgets. Review settings/metadata migrations and record incompatibilities before promoting the pin. Use [lifecycle](lifecycle.md) for fast Play Mode and [UI capabilities](ui-capabilities.md) for experimental gates. Installed plugin skills may target older Unity: record verified project exceptions instead of editing downloaded caches.

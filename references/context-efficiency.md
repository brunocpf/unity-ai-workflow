# Focused context and execution

Keep OpenSpec's lifecycle, required artifacts and full modified requirement blocks. Optimize retrieval and repetition, not acceptance.

- Start with project rules, docs/index.md, the active issue/change and affected source. Select one primary Unity skill and the OpenSpec operation for the current phase; add another only for an actual subtask. Read referenced sections when their trigger applies, not every transitive link. Never skip applicable rules because they are long.
- Keep docs/index.md as a short navigation page: current issue/change/handoff, source and authoring entrypoints, relevant ADRs/visual targets and the location of real check commands. It is not another status ledger or architecture copy. Check branch/diff against the handoff before trusting it.
- Discover live Unity commands through [targeted CLI tag listings](toolchain.md#beta12-capable-automation) when supported; request the full catalog only when needed.
- Within a session reuse already-read, unchanged policy and settled decisions. After a new session/compaction, reconstruct from the navigation and current artifacts; don't assume hidden prior context. Load archives, evaluation records, setup guides or dependency catalogs only for relevant history/setup/migration decisions.
- Give each fact one owner. Proposals explain scope; specs behavior; design decisions/deltas; tasks executable steps; verification evidence. Link across them and GitHub instead of restating whole documents. Small changes still satisfy the schema with short content. Preserve scenarios, negative cases and unresolved decisions.
- Use existing project check entrypoints. Keep complete logs as artifacts; return exit status, counts and actionable diagnostics to the conversation, with paths for inspection. Narrow file searches and read relevant sections before requesting whole logs or directories. Never truncate the evidence itself or hide failures.
- Run fast affected checks during editing and required delivery checks at the completion boundary. Re-run after relevant changes/failures; do not repeat an unchanged successful check per document or checklist. Gate rejection probes are required when introducing/changing the gate or when enforcement is doubtful, not every ordinary feature. CI/project policy may require broader runs. Fingerprint freshness and manual verdict rules still apply.
- When monitoring CI, request compact status for the current head and wait between snapshots (normally about 60 seconds). Retrieve logs for failures or stalled steps, not every successful poll. Local success is not hosted success; do not imply monitoring continues after the session unless actually scheduled.
- At a session boundary update one concise handoff: issue/change, exact revision plus dirty work, implemented/verified/pending state, decisions, evidence commands/paths, blockers and next action. Link current tasks; don't copy their checklist or retain conversation transcripts.

Keep current project policy focused on active rules, authority and unresolved constraints. Move dated administration/provisioning narratives to linked history only after reviewing which statements still govern work. Preserve anchors or redirects, fix relative links and retain unique decisions/evidence. This is an editorial review, never an automatic document-moving/deletion job. Historical status must be labeled by its date; current policy must retain applicable exceptions and acceptance owners.

The optional [starter PR template](../starter/.github/pull_request_template.md) links canonical evidence while retaining delivery, pending acceptance and cleanup. Merge its fields into a project's existing template rather than replacing it. For verbose verification output, the [starter runner](../starter/openspec/tooling/ci.py) offers `--quiet`: full per-run logs, concise status and bounded failure tails with failing exit codes preserved. See [setup](openspec-setup.md#verification-output) before adopting; these are implementations of the guidance above, not additional acceptance gates.

# Code organization and complete quality coverage

Formatting, syntax organization, semantic analysis and compilation are separate gates. Use [code quality](code-quality.md) for diagnostics, [IDE setup](ide.md) for compiler/namespace parity.

## Source conventions

- One top-level class/struct/record/interface/enum/delegate per matching filename. Partial declarations may use Type.Part.cs. Private nested implementation helpers stay with their owner; intentional public nested API types are reviewed as part of that owner. Assembly attributes/global imports may have dedicated files.
- One statement per line. Expand nonempty statement blocks. Required braces come from the configured style/compiler gate; no compressed constructor bodies or several assignments on one line.
- Blank lines separate constructors, methods and nested types. Related fields/events/simple properties may form compact groups. Keep accessors consistently formatted.
- Keep multi-property object configuration multiline. Wrap long parameter/argument lists (the supplied check uses 120 columns as its trigger). Break long fluent chains and complex expressions at meaningful boundaries; do not split string literals or URLs merely to hit a width. Formatting does not replace readability review.
- Logical namespaces follow the owning module, not every Assets/Unity directory segment. See ide.md. Vendor and genuine generated source retain their own organization.

[CodeOrganization](../starter/quality/CodeOrganization/Program.cs) uses the pinned SDK's Roslyn parser, not regular expressions over C#. It verifies top-level types including delegates/file-scoped namespaces, filename/partial naming, compressed statements, member separation and long list/configuration layout. It is read-only and fails syntax errors and empty file selections. Parse symbols are recorded by its caller; qualify relevant Editor/player conditional profiles. It is not a replacement compiler or a universal formatter, and does not try to rewrite source/assets or their metadata.

## Full owned-code coverage

Bootstrap copies [quality directory](../starter/quality/check.py) into tooling/quality/, including CodeOrganization and [coverage.json](../starter/quality/coverage.json). Set actual solution paths, owned project names and pureSourceRoots. Core/Application/Presentation files must appear in both Unity and SDK workspaces; tooling files require SDK coverage. Update this list when extracting pure modules. Add the CodeOrganization project to the hand-maintained SDK solution; it imports tooling/dotnet/Directory.Build.props for the same language/nullability/analyzer policy; pin the repository SDK, restore required projects and regenerate Unity projects before checking.

Run `python3 tooling/quality/check.py` from the project root (use python on Windows), or pass selected owned source paths for staged feedback. The supplied hook invokes the same driver. No full Unity player build is required per commit.

The driver inventories tracked/unignored owned C#, reads **evaluated Compile items and compiler properties through MSBuild**, verifies solution membership and coverage/profile parity, runs organization checks, then runs semantic dotnet format checks against the Unity and SDK solutions with explicit owned-file includes relative to the repository working directory. Use individual repository-relative file paths, never directory filters: both absolute includes in the kit fixture and `--include Assets/Game` in Pocket Arena silently selected no files in the pinned formatter. A trailing slash happened to work for that directory, but is not the contract; retain rejection probes for the exact invocation. [dotnet format options](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-format). Unity runtime, composition, UI, Editor and test sources must be represented; tooling belongs to its SDK projects. It fails missing projects, empty/uncovered selections, mismatched nullable/language/warnings settings, failed tools, recognized workspace-load problems and missing/nonpositive analyzer execution receipts. Both Code Style and Analyzer Reference phases must analyze every project containing selected owned source. A full run also rejects an owned project with no selected source; qualify conditional/platform-specific assembly profiles explicitly. The report records expected scope, phase counts and an incomplete/passed status. Local reports default to artifacts/quality. In CI pass `--artifacts <fresh-run-directory>/quality`; keep failed/incomplete runs distinct and retain that run’s exit status. Excluded `.g.cs`/`.generated.cs` files and extra owned package roots need deliberate provenance/scope handling.

The receipt parser uses the pinned formatter's English diagnostic output and fails closed if its protocol changes. Counts prove project-level execution, not that every rule ran on every file; compile-item coverage plus actual fault rejection remain necessary. When upgrading the SDK/formatter, requalify both positive and negative probes.

A workspace loader can fail while a formatter exits successfully. Resolve reference/SDK/generator/import problems and inspect its report; never accept a whitespace-only fallback. Confirm the project's installed formatter supports the generated Unity solution. If it cannot, implement explicit Unity-aware analysis projects referencing the actual installed assemblies/defines and verify the same compile-item inventory; record that alternative and its rejection probes. Do not quietly omit an assembly or broaden the pure test project to include Unity code.

Run all owned source in CI and selected files locally. Label results precisely: pure/whitespace-only jobs are **fast checks**, this driver reports **owned C# semantic/style checks** with all-owned or selected scope, and actual Unity compilation/tests/player acceptance are separate gates. Never promote a fast result to complete Unity validation. For large projects, an equivalent implementation can cache project evaluation keyed by toolchain/asmdef/package/config hashes and batch includes per project to avoid argument limits. Preserve uncovered-file failure and host-specific analysis; speed is not permission to drop semantic coverage. Compiler/analyzer warnings still require actual Unity and SDK gates; format success is not compile success.

## Rejection probes

After restore, run `python3 tooling/quality/test_organization.py` for the supplied [syntax regression cases](../starter/quality/test_organization.py). These test the checker itself. Run `python3 tooling/quality/test_semantic.py` for disposable [semantic/hook probes](../starter/quality/test_semantic.py): real SDK formatting rejects IDE0005 and IDE0240 through the adopted hook in both source layers; missing Compile coverage fails; clean baselines pass; receipt parser probes reject absent phases/projects and zero analyzers. Its isolated SDK workspaces do not certify actual Unity project loading or the Unity compiler. Retain the additional actual-project probes below.

In disposable fixtures/checkout changes, require the intended failure: a second top-level type, mismatched filename, two compact statements, badly formatted Unity adapter and pure file, unused imports (IDE0005), redundant nullable directives (IDE0240), a compiler/analyzer violation, nullable dereference without a local directive, an owned assembly skipped by semantic analysis, and an owned source missing from analysis projects, and a pure file included by Unity but omitted from the SDK harness. Include a private nested helper/valid partial file as positive cases. Run the same selected-file hook path, not only a standalone parser invocation. Remove faults and prove the clean baseline passes; report the exact gate/diagnostic. Keep code-organization acceptance separate from IDE completion/navigation acceptance.

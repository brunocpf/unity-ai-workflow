# C# quality and nullable references

Use the [owned-code EditorConfig](../starter/.editorconfig) at the Git/Unity project root. It adapts the supplied Godot/Adytum example: consistent Allman formatting, mandatory braces, explicit accessibility, focused correctness/async rules and naming. Keep enums/events PascalCase (no mandatory E prefix), interfaces I-prefixed, type parameters T-prefixed and private fields _camelCase. Use var when the initializer makes the type apparent. Avoid broad all-analyzers severity changes and duplicate/conflicting rules.

Rules target Assets/Game and tooling. Do not reformat vendor/generated code or edit PackageCache. Add scoped rules for an owned embedded package when one is created. Unity serialized YAML keeps whitespace handling separate from source. Public mutable fields are not the default API; validated authoring records may expose fields deliberately.

Explicit file/member/layout conventions and the syntax-aware checker are in [code organization](code-organization.md). All owned Unity layers receive semantic coverage; whitespace-only checking is insufficient.

## Enable nullable reference types

**Nullable annotations and warnings are enabled for all owned C#, including Unity adapters/UI/Editor and tests.** EditorConfig cannot enable the compiler's nullable context.

- Copy [csc.rsp](../starter/csc.rsp) beside **each owned asmdef**, including UI, runtime, Editor and test assemblies. It enables nullable and warnings-as-errors, pins the temporary language profile and explicitly passes the root EditorConfig to the compiler. Merge existing options deliberately; retain metadata. A single Assets/Game/csc.rsp does not recursively configure child asmdefs. Do not put our strict file in Assets/csc.rsp by default: that is a broad fallback and can affect third-party assemblies.
- Unity reference source selects an assembly-folder response file, otherwise the Assets-root fallback; the files are not automatically additive. Keep common flags synchronized in all owned response files. [Unity response-file lookup](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Editor/Mono/Scripting/Compilers/ResponseFileProvider.cs). Verify the selected Editor/player compiler arguments during bootstrap.
- Standalone source examples retain `#nullable enable` for safe copying. After verifying nullable in Unity, the SDK and generated IDE projects, remove redundant directives from adopted project code. IDE0240 is warning-level in owned source; do not suppress it or accept `#nullable disable` as an escape. SDK projects still require their own Nullable setting. [IDE0240 semantics](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/style-rules/ide0240).
- Choose the [language profile](language-profiles.md); C#9 is temporary and C#14 is the intended upgrade. Copy [Directory.Build.props](../starter/Directory.Build.props) to tooling/dotnet/ for SDK projects: Nullable=enable, the selected LangVersion (starter fallback 9.0), warnings as errors and build-time analysis. Pin a compatible .NET 10 SDK in the repository-root global.json used by local/CI dotnet commands; the host/test runtime and Unity API/language profiles remain separate.
- Unity-generated IDE projects receive owned nullable/language settings through [the generation hook](ide.md); never hand-edit those outputs or rely on Unity csc.rsp to configure VS Code. Generated source follows its generator's nullable context; validate the public boundary. For the modern profile, use [C#14 response options](../starter/language-profiles/csharp14.rsp) and the matching SDK/style configuration only after capability checks. Setting langversion cannot add compiler/runtime support that the selected Unity version lacks.
- New code has no blanket nullable disable, no global CS86xx suppression and no indiscriminate null-forgiving operator. Model optional values with `?`, validate external data and initialize required state through constructors/factories.
- Unity serialized references may start absent before authoring/wiring. Declare that honestly, validate in authoring and at runtime startup, then pass required references into runtime objects. Use a narrowly justified `null!` only when an enforced initialization invariant cannot be represented better. Nullable flow analysis does not detect a destroyed UnityEngine.Object: retain Unity-aware `== null` checks at engine boundaries; do not replace them with `is null`/`?.` and assume equivalent lifetime behavior.

Sources: [nullable compiler option](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/language#nullable), [nullable reference types](https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references).

## Enforcement

Install compatible analyzer assemblies in each actual compiler host; severity keys alone install nothing. The SDK starter sets analysis level 10.0-recommended for a pinned .NET 10 harness; do not assume Unity bundles the same analyzer version. Use the approved Roslyn-compatible analyzer set in Unity and record differences. Build-time style checks require EnforceCodeStyleInBuild and explicit diagnostics; formatting verification is a separate CI operation. [Analyzer configuration](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-options).

For the b2 evaluation profile, retain `-analyzerconfig:.editorconfig` in every owned response file. This was required by the b1 compiler probe; b2 Editor rejection probes remain pending. An installed analyzer DLL did not apply the intended severity in that b1 probe until this argument was supplied. Paths are relative to the compiler working directory (the project root in that evaluation), not the asmdef folder; inspect the emitted command and probe a spaced checkout path. If nested EditorConfigs exist, explicitly supply the relevant configuration files as well or keep the enforced policy in the root file. This flag selects configuration; it does not install analyzers.

One evaluated installation used `-analyzer:tooling/analyzers/Microsoft.Unity.Analyzers.dll` beside the configuration argument, with the pinned 1.24.0 DLL provisioned under tooling. Use either explicit compiler inclusion or the selected Unity import mechanism; avoid duplicate loading. Do not add a nonexistent DLL path to the starter or copy host-SDK analyzers blindly. Pin provenance/license and verify compatibility for each compiler host.

Treat new owned-code compiler/analyzer warnings as merge failures. When Unity cannot scope warning-as-error compilation cleanly, the Editor validation gate checks owned-code diagnostics and fails on unapproved warnings. Keep justified suppressions narrow, linked to their reason and revisit condition; avoid normalizing an ever-growing warning baseline. In existing projects, an explicit migration baseline may isolate old debt while rejecting new diagnostics.

Prove compiler and analyzer configuration with disposable deliberate faults: nullable dereference (CS8602) in a file **without** a nullable directive to prove the response-file default, an enabled analyzer rule and a formatting violation in an owned file; semantic IDE0005 unused-import and IDE0240 redundant-directive faults in both pure and Unity-only files; prove vendor files remain outside owned formatting scope. The Unity gate must run the actual Editor compiler, independently of the SDK gate. Assert the intended diagnostic ID and failure status, then remove the fault and prove the clean compile passes. A present DLL, a missing license, or an unrelated compilation failure is not proof. A successful IDE inspection does not satisfy this gate. Confirm current C# features against toolchain.md; do not enable future syntax through style rules before Unity supports it.

Adopted from the Godot reference: severity tiers, .NET-standard naming, build enforcement and generated/vendor boundaries. Adapted: no Godot exclusions, no C#14 rules in the temporary profile, no floating latest analyzer baseline, no blanket disposable/engine suppressions. GenerateDocumentationFile enables relevant build-time diagnostics; suppress only missing XML comments (CS1591), not nullable warnings.

After adopting Husky, run `python3 tooling/quality/test_semantic.py --husky` to exercise its real pre-commit entrypoint in disposable SDK fixtures, including organization faults. Without that option the probes call the hook driver directly. Actual Unity compilation and IDE capabilities remain separate checks.

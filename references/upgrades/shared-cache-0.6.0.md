# Adopt 0.6 shared cache

This changes instruction distribution, not game architecture or engineering tooling. Existing installations stay vendored until explicitly converted. Use the [0.5 process migration](decoupling-0.5.0.md) too when applicable; it includes hosted CI cache/timing guidance.

1. Preserve working changes and identify the current kit/version and mode. Review the candidate source at a clean commit. Inspect project-owned edits under docs/standards and the six kit skill directories. Move useful overrides/extra files into project-owned locations, repair links, and reconcile managed edits before conversion; the installer refuses to delete them.
2. Preview `install.py assess --target /game --mode shared` and `update --target /game --mode shared --dry-run`. Apply the reviewed update and run check. Shared adoption creates a portable pin, restore helper, managed ignore/routing blocks and local links. It does not move adopted game code, quality scripts, CI, assets, unrelated skills or independent process integrations.
3. Remove previously tracked managed copies from Git's index while retaining generated links. Review `git diff` and use `git add -u` for the known removed paths; do not force-add ignored links. Commit the pin/helper and reviewed root instructions/.gitignore. Verify `git ls-files` no longer lists docs/standards or the six linked kit skill directories and does not include .unity-workflow/local.json. Keep unrelated skills tracked. Inspect the staged diff before committing.
4. Check a fresh disposable clone/worktree with only committed files: restore the exact pin, check integrity, and verify skill discovery in each selected client. Exercise missing-cache offline failure and explicit exact-commit fetch. Confirm two projects on one pin share a cache and updating one does not move the other. Keep actual game checks runnable without the instruction cache.
5. If already shared, verify the current pin/links and change only what is missing. A mode-preserving update must not create duplicate copies. Shared mode exposes the complete example library; no per-project example copy is needed. Never edit the cache through docs/standards.
6. Roll back mode adoption with current `update --mode vendored`, check it, then revert only migration changes as needed and restore the prior reviewed kit. For later shared-version updates, revert the pin/helper/routing commit and run the restore helper. If reverting client selection, restore the matching committed ignore/routing files too. Preserve project-owned changes; missing permissions are a reason to choose vendoring explicitly, not to silently fall back to another version.

No automatic cleanup of old shared caches is provided: offline or unregistered projects may still need them. Global installation does not migrate any consuming project. Report the actual discovery/platform checks performed; a passing filesystem test is not a live-client result.

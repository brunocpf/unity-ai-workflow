# Adopt 0.5: engineering without process coupling

Apply directly from any older kit version. Do not first install superseded OpenSpec schemas, fingerprint helpers or process migrations. Unity/C#/package pins and gameplay architecture are unchanged. This migration changes workflow instructions and automation ownership, not gameplay.

1. **Assess and protect.** Inspect working changes, installed manifest, root/client instructions, hooks, CI and project-owned scripts. Use a migration branch/commit boundary; preserve unrelated work. Record the previous kit revision and rollback commands in the existing work record if needed. Assess the candidate and preview the managed update using [workflow updates](../workflow-updates.md). Reconcile local conflicts; never force overwrite customized tooling.
2. **Inventory real checks before deleting anything.** Inspect tooling/specs, active verification.json files, CI and hook callers. Extract every concrete command, target, timeout, environment/module requirement, report parser and manual procedure that still protects engineering behavior. Resolve indirect wrappers. Preserve custom security/platform jobs and current-run capture validation. Review commands before executing them; old records are not trusted executable input. Do not automatically convert historical receipts.
3. **Make checks standalone first.** Wire these checks into existing project-owned quality/test/build scripts and CI, independent of OpenSpec state or a change ID. Keep fast vs full semantic coverage explicit, full failure logs, stale-capture rejection and missing-report/coverage failure. The [optional runner](../engineering-checks.md) adds output handling only; it cannot replace suite/report validation. Run positive checks and relevant disposable faults to prove failure still propagates. Confirm actual game tests execute, rather than merely copying their command names. Keep the old gate until equivalent engineering coverage is demonstrated; report any blocked parity honestly.
4. **Separate the project's process choice.** If OpenSpec was adopted only because the kit required it and removal is in scope, preserve useful current requirements/design decisions in existing project docs/tests, then remove obsolete helpers, custom unity-game schema/config hooks, dedicated Node/npm dependency files, generated OpenSpec integrations and spec-only CI/hook jobs. Inspect both Codex and Claude discovery/command locations and automation callers. Do not delete shared Node tooling or unrelated integrations. Preserve historical specs/evidence in an explicitly historical location or retain them in place with a clear label; do not reseal, regenerate or fabricate acceptance. Pending decisions/checks remain pending. If the project independently wants OpenSpec, keep it under its own instructions and dependencies; remove only the kit's coupling. Never silently rewrite generated upstream skill content.
5. **Update instructions and remove redundancy.** Apply managed update/check. Reconcile project-owned AGENTS/CLAUDE, task skills, README, templates and CI references: remove mandatory proposals/tasks/maps/archive rules imposed by the kit. Preserve the project's GitHub Issues/Projects habits and useful decisions; no new management system is prescribed. Remove obsolete links and duplicate active policies after preserving unique content. Prefer concise project decisions and architecture, not new migration/status reports. Installer success alone does not migrate project-owned files.
6. **Verify and review.** Check the managed installation and client routing, run the engineering entrypoints from local and CI contexts, inspect effective owned-code/test coverage, and search active instructions/automation for old tooling/specs, unity-game and spec-only job dependencies. For a project removing OpenSpec, demonstrate checks run with no OpenSpec installation or change artifacts. Retained independent OpenSpec must not be required to run engineering commands. Review removed files for unique behavior/knowledge and repair references. Previously adopted equivalent behavior should be verified, not reimplemented.
7. **Rollback.** Revert only migration commits/project-owned edits, restore the previous kit using its reviewed installer, and reinstall previous dependencies from preserved locks if needed. Keep unrelated work and current game assets. Global installation and each consuming project are separate updates.

The installer removes obsolete *unmodified managed* sources but protects local edits. It never automatically deletes project-owned tooling/specs, generated integrations, requirements or history. Migration requires the review above; no destructive document conversion is automated.

## 0.5.1 hosted-CI guidance

The process migration above is unchanged. Adopt [Library caching and phase timing](../ci.md#github-hosted-runner-performance) in the existing GitHub-hosted workflow: inspect current caches/instrumentation first, apply only missing behavior, and preserve custom command/report validation. Keep the full engineering suites and a clean-import path. Validate cold, exact-hit and changed-source compatible-restore behavior, then compare warm timings including cache transfer. Updating managed guidance does not implement these changes in a game. Roll back the cache/timing workflow edits independently if they regress reliability or total time; no engine or runner-provider migration is required.

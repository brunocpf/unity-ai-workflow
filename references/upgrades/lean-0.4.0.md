# Full adoption of the lean workflow — 0.4

This replaces the kit's schema-1 evidence gate and redundant project-document baseline. OpenSpec 1.13.2, its generated integrations, required proposal/spec/design/tasks artifacts, scenario syntax and reconciliation/archive lifecycle stay unchanged. Architecture, authoring, localization, quality, visual freshness and target acceptance remain required. Use one migration change; no extra migration report.

## Procedure

1. Inspect the working tree, current PRs/change and project-specific rules/check commands. Preserve unrelated work. Create a migration branch/checkpoint. Inventory customized tooling and documentation before replacing them; carry forward their useful behavior, not their old file structure. Read this guide and the changed policy, not all historical upgrade guides.
2. Run the candidate installer `assess --target /game --examples none`, then `update --target /game --examples none --dry-run`, update and check. Resolve managed-file drift deliberately. The optional example pack is removed only when unmodified; preserve any project source adapted from examples. Use `--examples all` if complete offline reference access is needed. Global installation is a separate operation.
3. Consolidate active project documentation into README.md (commands/navigation), docs/project.md (product/platform/locale/visual decisions) and docs/architecture.md (implementation/authoring map and exceptions). Move unique decisions to their owner, repair references, then delete redundant indexes, status tables, feature briefs and completed handoffs. Keep substantial independently maintained documents when justified. Preserve historical acceptance artifacts and nonredundant project rules. Remove stale instruction references from AGENTS/CLAUDE/config/custom skills; don't copy kit policy into these documents.
4. Replace the project-owned schema/template and check.py/ci.py with the reviewed 0.4 equivalents, carrying forward custom test wrappers, target selection, suite/report parsers, retention and CI trust boundaries. Add migrate.py. Merge the config context changes without regenerating upstream OpenSpec skills or rerunning init. setup.py remains a new-project stager, not an upgrade tool. Update hooks/CI/PR automation that call fingerprint or interpret schema 1. Remove old resealing jobs and per-requirement result duplication. Keep independent quality/platform/security jobs; ensure actual game checks are still executed, not simply deleted as duplicates.
5. Convert active changes only. Review the real project verification entrypoint and supply it explicitly:

   ```sh
   python tooling/specs/migrate.py --change NAME --command-json '["{python}", "tooling/verify.py"]' --target "actual project target"
   # Inspect the proposed mapping, then repeat with --apply.
   ```

   The converter keeps requirement IDs and required check kinds, shares automated execution and resets manual verdicts to pending. Customize commands/scenario mapping to the actual project; the example path is not a guaranteed command. Consolidate equivalent manual checks if they genuinely share a review scope. Schema-2 changes are detected and left unchanged. For already archived current delivery, create a new migration change instead of rewriting the archive. Old historical receipts are neither refreshed nor subjected to schema-2 delivery.
6. Review applicable visual/authoring/device evidence. Reuse unchanged prior evidence only after explicitly reassessing its relevance; record that actual review with record-review. Recapture changed behavior; user/device acceptance cannot be invented. Run the shared delivery commands on the current checkout. Preserve the game's existing OpenSpec behavior and required checks while adapting its kit-specific bookkeeping.
7. Prove rejection of missing mappings, pending/failed manual checks, altered artifacts, command failures/timeouts and a source regression after a previous pass. Verify shared commands execute once per delivery, archive needs no resealing, both adopted clients route correctly, and optional-example links resolve to a pinned release. Run installed-file checks, strict OpenSpec validation and the game's affected quality/test/build gates. Do not claim full adoption while old gates or contradictory policy remain active.
8. Self-review the final diff for lost requirements, weakened test coverage, duplicate commands/status authorities, broken links and unowned customizations. Commit/publish under the project's normal delivery rules. Put actual results and remaining gaps in the existing change/PR. Roll back the migration commit and coupled helper/schema/CI changes together if needed; historical evidence remains untouched.

Full adoption means both managed standards **and** project-owned policy/tooling changed. A successful installer run alone is insufficient. The smaller artifact/read footprint is measurable; lower total AI token usage remains a hypothesis until compared on equivalent real tasks.
